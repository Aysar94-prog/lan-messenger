## 0.5 continuation

User asked directly, in English, for "seen" receipts and a per-chat unread count "like WhatsApp." Implemented as a new additive `LM4 SEEN`/`SEENACK` frame pair (see PROTOCOL.md "Seen receipts") sent asynchronously from the recipient's own periodic peer loop once the local user actually opens the conversation — never inline with ACK, since delivery and reading are genuinely separate events in time. No storage-format change: the existing per-message Status string just gained two more values, reused symmetrically for both directions — `Received`→`Read`→`Seen` on the reader's own incoming row (this is also exactly what "unread" counts, i.e. rows still `Received`), and `Delivered`→`Seen` on the sender's own outgoing row once a valid SEEN frame arrives for it. A group's aggregate status (already an existing concept for Delivered) got a third tier the same way: Seen only once every per-recipient row is Seen.

Marking read is a UI action, not a protocol one: both `Program.cs` (`Render()`) and `MainActivity.java` (`render()`) call the engine's new `MarkRead(conversation)` at the top of their existing per-tick render, guarded on Windows by `Visible && WindowState != Minimized` (Android already only renders while the Activity is resumed) — so a conversation left open counts as continuously "being read," matching a normal chat app, and a backgrounded/minimized/hidden window does not silently mark things read the way the existing minimized/hidden-notification tests already assume. Own-message bubbles now show ✓/✓✓ ticks (blue once Seen) instead of a bare status word; incoming bubbles show no status caption at all (a reader was never shown their own read-confirmation state before, and still isn't — only the sender sees ticks, matching WhatsApp). The conversation list gained a small unread-count badge (green circle, WhatsApp-style) per contact/group, computed from the new `Unread(conversation)`/`unread(conversation)` engine call.

Wire-compatible with 0.4.x on purpose (unlike the LM3→LM4 break): an unrecognized `SEEN` frame just makes the older peer close the connection, which the existing per-frame exception handling in `Receive()`/`receive()` already tolerates — verified by re-running the full suite, not just reasoned about. `tests/PeerHarness.java` and `tests/CsharpHarness/Program.cs` both gained matching `READ`/`UNREAD` commands so `tests/features.py` could drive this from Python like every other engine feature; the new assertions there cover the 1:1 round trip, unread clearing, and the group Delivered-until-all-Seen tiering, all against the real Java and C# engines over real loopback TLS. `tests/WindowsUi/Program.cs` got one new block (reusing the existing `second` peer and the existing `RestoreWindow` reflection helper) that drives a real send from the actual composer/Send button through to a real Seen confirmation and then asserts the literal "✓✓" appears in the rendered feed — this caught two direction mistakes (checking the wrong side's message row) during development, which is exactly the kind of bug this level of test would be expected to catch.

## 0.6 continuation

User asked (Arabic, detailed spec) for exactly four things, group-only, with explicit boundaries: (1) a member who receives a group message keeps a local copy it can forward to a fellow member who missed it; (2) a reconnecting member retrieves what it's missing from whoever's reachable, even if the original sender is offline, switching source if one drops; (3) a stable per-message ID prevents duplicate storage/display and the original sender's identity must be preserved; (4) a group message and its attachment expire 168h after their *original* send — re-forwarding never renews it — purged periodically and at startup before syncing, and rejected on receipt if already expired so an old device can't resurrect one. Explicit non-goals: don't touch 1:1 at all, no central server/blockchain, don't redesign membership/encryption/UI, don't retroactively delete old history.

The one design decision that needed real thought: (3) "preserve the original sender's identity" through a relay is a *security* requirement, not just a data-plumbing one. Before 0.6.0, a message's sender was authenticated purely by the live TLS connection it arrived on — fine for direct delivery, but if member B just forwarded A's bytes to C, C would be trusting *B's* connection for content claiming to be *A's*. That's exactly the "third-party relay with implicit trust" PROTOCOL.md already documented as explicitly ruled out (`No implicit certificate trust or third-party relay`), so a naive relay would have been a real, silent security regression — a compromised or malicious relaying member could otherwise put words in someone else's mouth. Fix: reuse the *existing* per-device RSA identity (already generated once per install for TLS, see Encrypted direct transport) to sign each group message's content; a relayed message is only trusted if the recipient has *already independently verified the original sender's own device* — receiving something via a relay never substitutes for that. No new key material, no group-shared secret, no redesign of membership or encryption — see PROTOCOL.md "Group relay and 7-day expiry (0.6.0)" for the exact frame formats and validation rules.

Wire/storage: `P` rows gained an 8th field (the peer's public key, captured at the same already-authenticated TLS handshake point fingerprints already come from — no new exchange). `M` rows gained two fields (signature, and a TTL-eligible flag) — old rows without them load as not-eligible, so **nothing existing is retroactively expired**, satisfying that boundary directly; new fields are populated only for group messages, so 1:1 rows are byte-for-byte unaffected. Two new frame types, both group-only and both requiring an already-`Trusted` connection like every other frame: `SYNCREQ`/`RELAY`/`RELAYACK`/`SYNCDONE` for pull-based sync (the *requester* always initiates, each cycle, against every reachable verified fellow member — this is what makes "C comes back and pulls from B" work with no special-casing for who reconnected first), and direct group `MSG` frames grow one optional field (the signature) *only when a group ID is present* — 1:1 `MSG` frames are still exactly 8 or 12 fields, unchanged. This does mean **group messaging itself is not backward-compatible with 0.4.x/0.5.0** (an old peer doesn't recognize the longer frame and just drops the connection, the same harmless way an unrecognized `SEEN` frame already does) — unlike Seen receipts, every member of a group needs 0.6.0 to keep exchanging group messages at all; 1:1 is completely unaffected regardless of version on either end.

Implementation is symmetric across `windows/PeerEngine.cs`/`android/.../PeerEngine.java` as always, plus `windows/SecureIdentity.cs`+`SecureChannel.cs`/`android/.../SecureIdentity.java` for signing and public-key capture, plus one persistent UI notice ("Group messages and their attachments are automatically deleted after 7 days of being sent") shown inside every group on both platforms. `tests/PeerHarness.java` gained a `RAWTIME` command (explicit-timestamp raw group frame, for expiry testing) and `tests/features.py` gained the four scenarios the user asked to be verified by, all against real Java/C# engines over real loopback TLS.

Two real bugs were caught and fixed during this work, both worth knowing about: (a) `Remember()`/`remember()` — called on *every* UDP discovery packet, i.e. every 2–3 seconds — rebuilt each `Peer` from scratch and, unlike fingerprint/verified which it already carried forward, silently dropped the newly-added public key back to empty each time; it would have self-healed on the next TLS handshake but left signature verification transiently and intermittently failing in between. Fixed on both platforms by threading the old public key through like the other fields. (b) The pre-existing `RAW` test harness command hardcoded a fixed, already-ancient timestamp (`1700000000000`) for constructing test MSG frames — harmless before 0.6.0, but it made one *existing, unrelated* test (duplicate-retry-after-clear) start failing once real expiry checking existed, since that timestamp is now genuinely expired for a real group. Fixed by making `RAW` use the actual current time by default and adding the separate `RAWTIME` command (explicit timestamp) for tests that specifically want an old one, like the new expiry tests — no existing call site needed to change.

`windows-dist-v06/LanMessenger.exe` and `LanMessenger-0.6.0.apk` (versionCode 8, existing signing key, `apksigner verify` OK, actual attachment storage path unchanged: `attachments/<original-sender-uuid>-<message-uuid>.sec` under the same per-install data directory as before) were built standalone in source; superseded by 0.7.0 below. `android/build.ps1`'s hardcoded output filename was bumped for both 0.5.0 and 0.6.0 in turn (it's easy to miss — it doesn't derive from the manifest version).

### 0.7.1 (Android only — real user acceptance testing on a physical device caught what compile-only checking couldn't)

User reported, in Arabic, three concrete Android problems after trying 0.7.0 for real: (1) the profile-picture tap did nothing; (2) the software keyboard covering most of the chat while typing, with no way to reclaim space; (3) no auto-scroll to the latest message when the keyboard opens. All three are Android-only per the user; Windows is untouched, still versioned 0.7.0.

(1) was a real bug in the 0.7.0 code, not a device-specific quirk: `showPeople()` built a clickable `ImageView` (`avatarView`) with the change-picture listener, but only ever *added it to the screen* in the branch where an avatar image already existed; the no-avatar-yet fallback (everyone's default state) added a *different*, non-clickable `TextView` showing the initial letter instead. So the visible circle had no listener, and the listener lived on an element that was never shown — this is exactly the kind of bug that compiling cleanly and even a code read can miss, and is why the HANDOFF note above calling this "done" for Android was wrong. Fixed by wrapping both the image and the initial-letter fallback in one `FrameLayout` that is always added and always carries the click listener, regardless of which child is currently visible.

(2)/(3) are new, driven by one shared mechanism: `showChat()` now attaches a `ViewTreeObserver.OnGlobalLayoutListener` to the window's decor view (the standard Android technique for detecting the soft keyboard, since there's no direct callback for it) that compares the window's visible frame height to the full window height; when the gap exceeds ~15% of screen height, the keyboard is inferred to be open. On the open transition it sets `Verify device`/`More` (and the group-expiry notice, if present) to `GONE` — leaving just the back arrow, per the user's literal ask — and scrolls the feed to the bottom once; on close it restores them. The listener is added at the end of `showChat()` and explicitly removed at the top of `frame()` (which both `showPeople()`/`showChat()` call first) so it never accumulates duplicates across navigation. This is a heuristic (screen-height-ratio), not an official API, but it is the standard approach absent `WindowInsets` APIs this codebase doesn't otherwise use.

Verified: full `tests/run.ps1` still passes (these are Android-UI-only changes, invisible to the engine/Windows-UI test suite — expected, not meaningful new coverage) and `javac` compiles clean; **there is still no automated or manual visual/interactive check of the Android UI in this repo** — everything Android-UI-shaped, including whether this specific fix actually resolves what the user saw, is going on their direct report and code reasoning, not a screenshot or device test the way Windows gets. `LanMessenger-0.7.1.apk` (versionCode 10, existing signing key, `apksigner verify` OK) built standalone. If another Android UI issue gets reported, treat it as equally plausible that it's a real bug like this one, not user error — this codebase's Android UI has now demonstrably shipped with at least one dead control.

### 0.7.2 (Windows) — crash fix for the 0.7.1 mini-avatar feature

User ran the actual `windows-dist-v071` build and hit a real crash, reported as a raw .NET unhandled-exception dialog: `System.ArgumentException: Parameter is not valid` inside `PictureBox.ImageRectangleFromSizeMode` during `OnPaint`. That exact message is GDI+'s signature error for "this `Image`/`Bitmap` object is disposed or otherwise invalid" — not a sizing or layout bug.

Root cause: 0.7.1's `SenderRow()` pointed a message bubble's mini-avatar `PictureBox.Image` directly at the shared toolbar `avatarImage` field for every "mine" bubble (`avatar.Image=avatarImage`, no copy). `ChangeAvatar()` (existing code, line ~239) does `avatarImage?.Dispose(); avatarImage=thumb;` whenever you pick a new photo — correct for the toolbar's own `PictureBox`, which gets its `.Image` reassigned in the same call, but every *already-rendered message bubble* from earlier in the conversation still held a reference to that same now-disposed `Bitmap` instance. The next time any of those older bubbles repainted (scrolling, window resize, restore-from-minimize), GDI+ tried to read size/pixel data from a disposed native handle and threw. This is exactly the class of shared-mutable-resource bug the codebase's own existing pattern (dispose only *freshly drawn, per-instance* bitmaps, e.g. the attachment-thumbnail `picture.Disposed+=(_,_)=>thumbnail.Dispose();` pattern already in this file) was designed to avoid — 0.7.1's avatar branch didn't follow it and shared the cached instance directly instead.

Fix: `SenderRow()` now clones the avatar (`new Bitmap(avatarImage)`) per bubble when `mine&&avatarImage!=null`, and disposes that clone on the `PictureBox`'s own `Disposed` event — identical lifecycle to the initial-letter fallback branch right next to it. Each bubble now owns an independent copy; changing your photo later disposes only the shared toolbar source, never anything a bubble is still painting from. One-line-pattern fix, no behavior change otherwise.

Verified: full `tests/run.ps1` re-run, passed including the native `WindowsUi` screenshot test; re-read the resulting `windows-seen.png` and confirmed the avatars still render correctly after the fix. `windows/LanMessenger.csproj`/`AppVersion` bumped `0.7.1`→`0.7.2` (Windows) — deliberately re-versioned rather than silently patched, since a real broken build (0.7.1) had already reached the user. `windows-dist-v072/LanMessenger.exe` built standalone (old `windows-dist-v071` folder removed). Android unaffected, unchanged, stays 0.7.2 (coincidentally the same number as Windows now — the two platforms version independently, this is not a synchronized release).

### 0.7.3 (both platforms) — profile pictures now actually shared with the other side

User pointed out that after the previous avatar work, the picture only ever showed on your own device — the other person never saw it — and asked for it to actually be sent. This is the feature that was explicitly offered and declined back in 0.7.0 ("local only for now"); the user has now asked for it, so it's implemented here. Bumped both platforms together (`0.7.2`→`0.7.3`) since this is a wire-protocol change, not a single-platform UI tweak like the last several rounds.

Design mirrors Seen receipts, not group relay: an avatar travels directly between two devices that have already verified each other — never through a third party — so unlike group messages it needs no signature, just the same TLS mutual-authentication and Trust gate everything else already uses. New persisted `Peer` fields `SentAvatarHash`/`ReceivedAvatarHash` (C# `PeerEngine.cs`, mirrored as `sentAvatarHash`/`receivedAvatarHash` in Java `PeerEngine.java`) track, per peer, the hash of the avatar we last successfully pushed to them and the hash of the avatar we last received from them — the same "row grows, old rows default to empty" backward-compatible pattern used for every previous P-row extension (now 10 tab-separated fields; older 5/7/8-field rows still load fine). New wire frames `LM4 AVATAR <sender-id> <hash> <byte-length>` (header, then raw bytes if length>0) and `LM4 AVATARACK <hash>`, dispatched in `Receive()`/`receive()` alongside the existing SEEN/SYNCREQ cases, and pushed from `Deliver()`/`deliver()`'s per-peer loop — the same "compare local state to last-acknowledged state, push on mismatch, only advance local state after a valid ACK" pattern SEEN already uses, so a dropped connection just retries next ~2s tick like everything else in that loop. A push only happens `if(peer.Trusted)`/`if(p.trusted())`; an unverified or not-yet-verified peer never receives anyone's picture. A received avatar is capped at 2 MB (`MaxAvatarSize`/`MAX_AVATAR_SIZE`) and hash-checked before being trusted, then stored the same way as the local avatar and every attachment: an encrypted per-peer file, `avatars/<peer-device-id>.sec`, decrypted with the same storage protector. Clearing your own avatar (hash becomes `""`) propagates the same way — the peer deletes its stored copy of your picture.

UI: both platforms' message-bubble mini-avatar (added in 0.7.1 Windows / 0.7.2 Android) now checks for a real received avatar (`engine.PeerAvatar(senderId)` / `e.peerAvatar(m.from)`) before falling back to the colored initial, for the non-"mine" case. On Windows this decodes a fresh `Image` per bubble via the existing `TryImageThumbnail` helper and disposes it on that `PictureBox`'s own `Disposed` event — deliberately NOT sharing a cached instance across bubbles, learning directly from the 0.7.2 crash fix above. On Android this reuses the existing `inlineBitmap` decode-per-render-pass pattern (already proven safe, see the 0.7.2 Android continuation) — no new disposal risk there since Android already recycles every bitmap in the feed tree together at the start of the next `render()` call. Deliberately did not touch the contact-list circle or the chat-header avatar on either platform — matching the literal ask ("the picture doesn't reach the other side in messages") and keeping scope proportionate; can be extended later if asked.

Verification: added `SETAVATAR`/`CLEARAVATAR`/`PEERAVATAR` commands to both test harnesses (`tests/PeerHarness.java`, `tests/CsharpHarness/Program.cs`) and a new scenario in `tests/features.py` — one verified device sets an avatar, the other side receives it (hash+length match), then the first clears it and the other side's copy disappears too. First attempt at this test used peer `a`, which — as the surrounding test file already documents — gets deliberately stopped earlier in the same run for an unrelated offline-sender relay test and is never restarted; that made the harness process's stdin pipe closed by the time my new code ran, producing a Python `OSError` that looked at first like a real product bug. Re-read the file, confirmed `a` is intentionally dead at that point, and switched the test to use `b`/`c` (verified with each other from the start of the file, never stopped) instead — real test-authoring mistake, not an app bug, same category flagged elsewhere in this document. Full suite passes after that fix, including this new scenario; Windows UI re-confirmed via a fresh `windows-seen.png` (no avatar set in that specific scripted scenario, so it correctly still shows colored-initial circles — this run didn't visually exercise a real received photo, only the protocol delivery, which the Python test scenario does check directly via hash/length). `windows-dist-v073/LanMessenger.exe` and `LanMessenger-0.7.3.apk` (versionCode 12, existing signing key, `apksigner verify` OK) built standalone. `PROTOCOL.md` gained an "Avatar sharing (0.7.3)" section documenting the exact frame format and trust rationale.

### 0.7.4 (both platforms) — attachments up to 1 GiB, streamed instead of loaded whole into memory

User asked why the current transfer system hangs on large files. Traced it precisely (not guessed): `Send()`'s click handler (both platforms) called the engine's queue method directly and synchronously on the UI/main thread, which does hashing + at-rest encryption + a full local-state rewrite before returning — for a large file this really freezes the UI (not just "feels slow"), and on Android risks a genuine ANR. Explained this, then the user asked for a real design to raise the cap to 1 GiB, explicitly agreeing to trade away per-chunk at-rest authentication for the ability to stream (see PROTOCOL.md's new "Streamed attachments" section for the exact design) — a real, deliberate security-posture decision made with the user, not something decided unilaterally.

This was the single largest, riskiest change of the session — a full rewrite of the attachment pipeline on both platforms (local storage format, network send/receive, group relay send/receive, the Windows and Android UI attach/draft/send/export/preview flows) — and it surfaced **six real, independent bugs**, five of them only found by actually running the full test suite repeatedly and chasing failures to ground truth rather than guessing:

1. **Java `CipherOutputStream.close()` cascades into closing the wrapped `FileOutputStream`.** The new streaming store tried to `fsync` the file *after* that close, on an already-closed descriptor — surfaced as `SyncFailedException` on the very first attachment test. Fixed by driving `Cipher.update()`/`doFinal()` manually instead of through `CipherOutputStream`, so the code controls exactly when the file closes. (The C# side never had this problem — `CryptoStream`'s constructor takes an explicit `leaveOpen: true`.)
2. **An empty-but-present attachment (`new byte[0]`) was silently treated as "no attachment at all".** `QueueFile(byte[])`'s wrapper only built a source stream `if(data.Length>0)`, collapsing a deliberate 0-byte file to `null` — which then failed message-content validation ("Messages must contain 1–2000 characters") for the existing, previously-passing "empty attachment" test. Fixed by always wrapping `data`, even when empty; `null` now means "no attachment" only when a caller (`Queue`) explicitly passes it.
3. **The most serious one: re-syncing a message the recipient already has could delete the attachment they already legitimately stored for it.** Both `Receive()`/`receive()` and the group SYNCREQ receive loop wrote the incoming stream to disk *before* checking whether the message was a duplicate, then deleted the file on any non-insert path — which didn't distinguish "genuinely rejected" from "a normal duplicate re-sync of something already present". Every group member re-syncs constantly with every other member sharing a group, so this reliably destroyed real attachments during ordinary background traffic, not just on some rare retry. Fixed by explicitly separating "cleared/hidden, never resurrect" (still deletes, correct — this is the existing "duplicate retries do not restore cleared history" guarantee) from "duplicate of a still-present message" (never deletes now) in both platforms' receive paths.
4. **Java sockets have no native write-timeout.** Unlike the read timeout set once at connect time (`setSoTimeout`), a stuck peer on the *reading* end could block a *sending* thread on `OutputStream.write()` forever — and with only 2–6 threads shared by a whole process for every peer's send and receive work, just one or two such stalls silently starved everything else. This surfaced as a real, reproducible test hang (a Seen receipt that should arrive in ~2 seconds just never did, no exception, no timeout, for 90+ real seconds) — traced by adding temporary file-based diagnostic logging directly into the delivery loop's catch blocks (since a background-thread exception doesn't reach the test harness's stdout protocol) until the exact stuck call was identified. Fixed with a watchdog (`NetworkTimeoutOutputStream`) that closes the socket if a single chunk write doesn't finish within 45 seconds — applied everywhere a raw socket write happens (the control-frame `write()` helper, avatar push, attachment send), not just the new streaming path.
5. **The actual root cause of that same hang, once found: `File.renameTo()` on Java silently returns `false` (doesn't throw) if the destination already exists — this is Windows-specific Java behavior, unlike a POSIX rename.** The new streaming store used this for its atomic temp-file-to-final-path swap; for an attachment already on disk (exactly the "duplicate re-sync" scenario above, after fixing bug 3) every retry failed identically and forever with "Cannot save attachment", which meant `deliver()` returned early on every cycle before ever reaching the unrelated Seen-receipt code further down the same method — explaining why an apparently unrelated feature (Seen) seemed to break. Root-caused by adding message-ID-level diagnostic logging and reading the exact exception, not by guessing. Fixed by switching to `java.nio.file.Files.move(..., REPLACE_EXISTING)`, which correctly replaces the destination on every platform — also applied to `setAvatar`/`setPeerAvatar`'s same `renameTo` pattern, a **pre-existing latent bug** from the 0.7.0/0.7.3 avatar work that just never happened to hit the "already exists" case in earlier tests (changing your avatar a *second* time would have silently failed the same way).
6. **Windows' picked-filename display name vs. on-disk name.** The old `Send()` always passed the explicit `pendingAttachmentName` through to the queue call; the new path-based `QueueFileFromPathAsync` re-derived the name from the file path instead, silently dropping a caller-supplied display name (harmless for a real file picker, where they're the same string, but a real behavior change). Caught by the native Windows UI test, which deliberately uses a display name that differs from the underlying temp file's name. Fixed by adding an optional `displayName` parameter that takes priority over the path-derived name.

Design summary (also in PROTOCOL.md): every attachment read/write, on both the local-storage and network path, now moves through fixed 1 MiB chunks instead of one large buffer — this is what makes 1 GiB (`MaxFileSize`/`MAX_FILE_SIZE`, up from 200 MiB) safe without an OOM risk, particularly on Android. New on-disk attachment format (`LMATCS1` magic + length-prefixed DPAPI/Keystore-wrapped per-attachment AES-256-CBC key/IV + streamed ciphertext) replaces whole-file `Protect`/`protect`; attachments from before 0.7.4 are still read correctly via the old path, auto-detected by the absence of the magic prefix — nothing is migrated or re-encrypted on upgrade. Wire bytes are unchanged (same frames, same total length — only the number of `read`/`write` calls moving them differs), so this is fully wire-compatible with older versions; an older peer is just still bound by its own lower cap. `Send()` on both platforms is now properly asynchronous/backgrounded (the actual fix for the original UI-freeze complaint), with a throttled `TransferProgress` event surfaced as "Sending NN%" directly in the message's own status line. Windows' attach flow now tracks a file *path* instead of reading the whole file into memory up front; Android's tracks a `Uri` (+ size, queried via `OpenableColumns`, with a bounded-read fallback for the rare picker that doesn't report size). Inline thumbnails (both draft preview and the chat feed itself) are now skipped above a 20 MB threshold, since decoding one means fully decrypting the attachment — otherwise scrolling a conversation with even one large file in it would silently decrypt it on every render.

Verification: added a new `tests/features.py` scenario sending a ~3 MB payload (several times the 1 MiB chunk size, so it actually exercises the chunking loop, not just a single-chunk payload that could hide a chunking bug) and verifying it round-trips byte-for-byte. Full suite (`tests/run.ps1`) passes at the *original* 30-second `wait_for` timeout (briefly raised to 90s mid-investigation specifically to rule out "just needs more time" before concluding bug 4/5 were genuine deadlocks, then put back). Windows UI re-confirmed via fresh `windows.png`/`windows-seen.png` screenshots, including the attachment-draft/inline-image/Save-Open-button assertions. `windows-dist-v074/LanMessenger.exe` and `LanMessenger-0.7.4.apk` (versionCode 13, existing signing key, `apksigner verify` OK) built standalone. **Not done, flagged explicitly rather than silently skipped:** an actual end-to-end ~1 GiB transfer has not been run on a real device/real Wi-Fi — the automated suite deliberately uses a much smaller multi-chunk payload to keep the suite fast; a real near-cap transfer is real acceptance-testing work, same category as every other physical-device gap already tracked in this file.
