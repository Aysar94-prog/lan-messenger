# Shared call-frame fixture corpus -- read by BOTH parsers.
#
# tests/video-contract/SharedFrameFixtureCheck.java runs it against
#   android/src/net/lanmsg/chat/CallSignaling.java + CallVideoProtocol.java
# tests/CsharpHarness/CallFrameFixtureCheck.cs runs it against
#   windows/CallSignaling.cs + CallVideoProtocol.cs
#
# Each parser must reach the SAME verdict for every record, and that verdict must also match the
# expectation written here by hand. Three-way agreement is the point: a change that makes Windows
# more permissive than Android (or the reverse) breaks interop and is caught here rather than on a
# phone.
#
# Record format (one per line, '|' separated, no '|' may appear in a payload):
#   name|expectParse|expectValid|payload
#     expectParse  1 = the frame must parse, 0 = the frame must be refused by the envelope
#     expectValid  1 = CallVideoProtocol.valid must accept, 0 = must reject, - = not applicable
#                  (only meaningful for a parsed frame whose protocolVersion is 2)
#     payload      the exact JSON text to frame, OR b64:<base64 of the complete wire bytes> when
#                  the case is about bytes rather than text (bad length prefix, invalid UTF-8, ...)
#
# Payloads are JSON TEXT and are used exactly as written, which means an SDP sample keeps its CRLF as
# the two-character escape \r\n: that escape is what belongs inside a JSON string. Unescaping it while
# reading the file would put a raw control character into the JSON, and both parsers would then refuse
# the frame as malformed JSON -- a real divergence being reported for a fixture bug.
#
# Lines beginning with '#' are comments. "#SAMPLE <name><TAB><text>" defines a reusable text sample,
# and @name@ inside a payload is replaced by it. The samples exist purely to keep the records
# readable; they are expanded identically on both sides before use.

# ── transport profile: SAVP and SAVPF are the two legal profiles ─────────────────
# The two differ by the "secure RTP with a feedback extension" flag and nothing else -- same
# ICE/DTLS transport -- and real stacks disagree about which one they write: SIPSorcery 10.0.17
# (the Windows adapter) writes UDP/TLS/RTP/SAVP, libwebrtc writes UDP/TLS/RTP/SAVPF. Accepting
# only SAVPF therefore rejected every SDP a real peer produced, and the rejection surfaced as a
# silent EndReason.MediaError because the sender's validator threw and the handler discarded the
# exception. Both ports must accept both. TCP is still refused -- a different transport, not a
# different profile -- and so is any other token, including the near-miss SAVPX.
